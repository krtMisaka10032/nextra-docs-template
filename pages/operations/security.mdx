# 安全模型

nl2sql-proxy 的目标是“**不允许外部直连数据库，所有操作经由本服务的单一接口**”。安全能力是分层的，单层被绕过时仍有下一层兜底，但每一层都有明确边界。

> 本文中的库名、账号均为 mock，仅用于演示。

## 分层防护

| 层 | 机制 | 边界 |
| --- | --- | --- |
| 网络层 | 默认只监听 `127.0.0.1`；对外走反代/隧道 + TLS | 服务本身不提供 TLS、限流 |
| 认证层 | 单一 API Key（`X-API-Key` / Bearer），恒时比较 | 没有多用户/多角色，无法按人审计权限 |
| 语句策略层 | 单语句、只读复检、函数黑名单、无 WHERE 写拒绝、LIMIT 控制 | 应用层防护，不是数据库沙箱 |
| 写门禁 | 写操作（含 DDL）必须 `confirm_write=true`；写前可 `dry_run` | 持有 Key 的调用方可自行确认 |
| 数据库权限层 | 使用配置的数据库账号连接 | 若用超级用户，代理进程即拥有全部权限 |
| 审计层 | 每次进入引擎的请求落 SQLite | 401 请求不进入引擎，不落审计 |

## API Key 管理

- 只有一个管理 Key，HTTP 与 MCP 共用
- 推荐通过环境变量注入，不写进配置文件：

```bash
export NL2SQL_API_KEY='强随机字符串'
```

- 审计只记录 Key 的提示符（前 4 位 + SHA-256 前 8 位），不会存明文
- 轮换 Key：更新环境变量/配置后重启服务；所有客户端需同步更新
- 不要把 Key 放在前端页面、URL 参数或可公开的日志里

## 写操作的双重门禁

1. **请求级确认**：必须显式传 `confirm_write=true`，否则返回 `POLICY_WRITE_CONFIRM_REQUIRED`
2. **语句级约束**：无 WHERE 的 UPDATE/DELETE 拒绝；多语句拒绝；事务/SET/GRANT/COPY 拒绝

另外，写操作会自动追加 `RETURNING *`，把受影响行回显出来，便于调用方确认影响范围。

NL 模式不允许任何写操作，因此 `confirm_write` 在 NL 模式下没有意义。

## 数据库账号（重要）

示例配置可能使用高权限账号（例如数据库管理员）并以本机 trust 认证连接，这等价于**代理进程拥有数据库上帝权限**。生产环境应改为最小权限账号：

```sql
-- 只读分析角色示例
CREATE ROLE nl2sql_ro LOGIN PASSWORD '强随机密码';
GRANT CONNECT ON DATABASE sales TO nl2sql_ro;
GRANT USAGE ON SCHEMA public TO nl2sql_ro;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO nl2sql_ro;
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT SELECT ON TABLES TO nl2sql_ro;
```

- 需要写能力时，单独授权具体表的具体操作，不要授予全库写权限
- `ALTER DEFAULT PRIVILEGES` 需由对象所有者执行，或调整授权方式
- 修改后更新 `datasources[].user` / `password`（示例中为 `demo_user`）

## 遗留风险：PostgreSQL 对外暴露

项目说明中记录了一个已知风险：`pg_hba.conf` 可能存在类似

```text
host sales sales 0.0.0.0/0 md5
```

的规则，意味着业务库对全网开放了密码爆破面，与“禁止外部直连”的目标冲突。

处理建议：

1. 确认没有其他系统依赖该规则
2. 注释该行，仅保留 `127.0.0.1` 的本地连接
3. `pg_ctl reload` 或 `SELECT pg_reload_conf();`
4. 用 `ss -lntp` 确认数据库没有监听公网地址

## 对外暴露

服务默认监听 `127.0.0.1`。需要跨机访问时：

- **SSH 隧道**（最简单）：

```bash
ssh -L 8731:127.0.0.1:8731 user@server
```

- **nginx 反向代理 + TLS**：

```nginx
server {
    listen 443 ssl;
    server_name nl2sql.example.com;
    # ssl_certificate ...; ssl_certificate_key ...;

    location / {
        proxy_pass http://127.0.0.1:8731;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}
```

- 在反代层补充访问控制、限流与日志；服务本身没有内置限流
- 不要直接把 `8731` 端口暴露到公网

## 数据会发给谁

NL 模式依赖外部模型（qoder CLI → `DeepSeek-Flash`）。发送内容包括：

- 用户问题
- 剪枝后的表结构（表名、列名、类型、注释）
- 业务术语表与 few-shot 样例
- 修复轮次中上一次的 SQL 与数据库报错文本

**查询结果行不会发送给模型**。如果表结构、字段名或业务术语本身属于敏感信息，需要评估模型服务的数据处理政策后再启用 NL 模式；也可以只用 `mode=sql`。

## 安全检查清单

- [ ] `api_key` 为强随机值，且未提交到代码仓库
- [ ] 服务只监听 `127.0.0.1`，对外有 TLS 与访问控制
- [ ] 数据库使用最小权限账号，而非超级用户
- [ ] `pg_hba.conf` 已收回公网访问
- [ ] 写操作在调用方有审批/确认流程
- [ ] 审计库文件权限为 600，纳入备份与留存管理
- [ ] 了解 NL 模式会把问题与表结构发送给模型服务
- [ ] 反向代理层配置了限流与监控
